# Private pilot security and privacy

Security and privacy are release gates for the five-couple private pilot. The pilot stays on hold until the controls below pass with synthetic accounts and documents. PM approval is required before provisioning any paid service, setting a paid spend limit, or inviting real participants. AI processing has a separate enablement gate. Manual quote entry remains available if AI is disabled or unavailable.

## Architecture and access

Use Supabase Auth, Postgres, and private Storage with the existing frontend and server. Keep an authoritative, versioned workspace record in Postgres, with separate membership, invitation, and attachment metadata. Reuse existing workspace transitions and financial approval rules server-side. The browser sends an explicit action and the version it reviewed. Postgres checks membership and the expected version in the write transaction. Limit raw database access to the intended read paths and guarded write operations. Avoid a new queue, synchronization service, or public sharing feature. Link any future helper flow to Issue #4 and gate its release on separate tests for its task-only permissions. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

| Role | Pilot permissions |
|---|---|
| Owner | Read and edit own workspace, manage invitations and partner access, and request workspace deletion. |
| Partner | Read and edit the invited workspace and its attachments, subject to existing financial approval gates. |
| Pending invite, signed-out account, unrelated account, or revoked partner | No workspace or attachment access. |

## Threat model and defensive verification

Use two synthetic workspaces, each with its own owner and distinct quotes, payments, and files. Add a partner, a pending invitee, a revoked partner with a previously issued session, and a signed-out browser. Run positive and negative cases against the actual staging API, Postgres policies, and Storage endpoints as well as the UI. Verify that a partner can edit authorized records and cannot change roles, manage invitations, or delete the workspace. Verify that an owner’s privileges stop at the workspace boundary. Keep test artifacts free of credentials and real documents.

| Risk | Pilot control | Evidence required |
|---|---|---|
| Unauthorized workspace or attachment access | Default-deny database grants and row-level security (RLS) based on current membership. Scope every row, object path, and related record to its workspace. Keep Storage private. Use authenticated downloads with operation-specific Storage RLS, no bearer share links, and no caching of sensitive responses. | Authorized users can read their files. Signed-out users, unrelated users, and revoked partners cannot read, list, change, or delete protected records or files. Pilot accounts cannot create signed URLs. Cross-workspace attachment associations and direct writes outside approved transitions are denied. |
| Account or session takeover | Invite-only Supabase Auth with verified email, short-lived sessions, server-held tokens in Secure, HttpOnly, SameSite cookies, CSRF protection for writes, and explicit logout. Allow only approved HTTPS redirect destinations. Require MFA for infrastructure administrators and fresh authentication for sensitive owner actions. | Verify HTTPS enforcement, cookie flags, expiry, logout, fresh authentication, and rejection of unapproved redirects and cross-origin writes. Confirm that signing out clears browser state and that privileged changes reject stale sessions. |
| Invitation misuse or ineffective revocation | Owner-controlled, single-use invitations tied to the recipient’s verified email and workspace, with at most one hour of validity. Revoke invitations and memberships in Postgres. Check current membership on each request, including document reads and extraction. | An intended recipient can accept once. Wrong-account, replayed, expired, and revoked invites fail. A previously issued session loses workspace and file access after membership revocation. |
| API abuse or unexpected spending | Authenticate and authorize before work starts. Rate-limit auth and invites, uploads, and extraction. Use a shared Postgres counter to enforce per-user, per-workspace, and total limits across requests. Reserve budget before dispatch, bound request size and model output, deduplicate retries, and keep a server-side kill switch. | Concurrent requests and retries respect the limits. Requests declined for permission, size, or quota trigger zero provider calls. Exhausting the cap preserves manual entry. |
| Secret disclosure | Use managed runtime secrets and least-privilege service identities. Separate staging and pilot credentials. Isolate any privileged Storage credentials to server-managed file writes and cleanup after database authorization. Keep document content, tokens, cookies, and invite links out of application and CI logs. | Inspect browser bundles, logs, and build artifacts. Verify secret and dependency scanning, credential rotation, and alert ownership. Resolve material findings before invitations go out. |
| Concurrent edits or data loss | Reject stale writes and show the user how to reload and reapply their changes. Make financial transitions atomic and retries idempotent. Test a backup and recovery procedure for both the database and private files. | Two editors updating the same version produce one accepted write and one conflict. Retries leave one payment or booking. A synthetic restore reconciles quote history, file references, and committed balances. |
| AI provider processing or retention | Send the selected document or excerpt only after the user chooses AI extraction and sees the provider disclosure. Use the approved project, model, and location. Disable request/response logging, caching, grounding, and provider-side file persistence. Treat model output as a draft. | Capture sanitized configuration evidence and verify that disabled or misconfigured AI sends zero calls. Check that app telemetry contains usage metadata only and that AI output cannot bypass quote review or change commitments. |

Use HTTPS for all pilot surfaces and require TLS for direct database connections. On the server, accept PDF, PNG, and JPEG only. Proposed limits are one file, 10 MB, 10 PDF pages, and 20 megapixels per image. Verify actual file type and structure, reject malformed, encrypted, or active-content PDFs, and scan uploads before making them eligible for download or extraction. Enforce byte and MIME restrictions on the bucket as a second control. Block direct client uploads that bypass validation. Serve verified files as private downloads with generated object keys and log only sanitized metadata. [Supabase Storage controls](https://supabase.com/docs/guides/storage/security/access-control) · [Storage policy helpers](https://supabase.com/docs/guides/storage/schema/helper-functions) · [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

Give participants a privacy notice before upload and a specific disclosure before AI extraction. Explain the processors, purposes, processing locations, retention periods, deletion contact, and manual option. Agree on the retention window with PM before launch. For the five-couple pilot, use a verified, operator-assisted account and workspace deletion workflow. Remove access promptly, delete private objects through the Storage API, remove associated active records and derivatives for the approved deletion scope, and confirm completion. Account deletion must respect shared workspace ownership. Document backup expiry and reapply completed deletions after a restore. Supabase database backups exclude Storage object bytes, so verify file recovery separately. [Supabase object deletion](https://supabase.com/docs/guides/storage/management/delete-objects) · [Supabase database backups](https://supabase.com/docs/guides/platform/backups)

## AI configuration and cost

Recommend Google Cloud’s Gemini Enterprise Agent Platform with the pinned `gemini-3.5-flash-lite` model, pay-as-you-go standard inference, and a supported non-global endpoint approved for the participant data. Use one server-side request for each deliberate extraction. Use a least-privilege workload identity in a dedicated project. Real documents must never be sent through the free Gemini Developer API or AI Studio. Use synthetic documents for verification, with manual entry as the pilot default until provider processing is approved. [Model documentation](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite) · [Gemini Developer API terms](https://ai.google.dev/gemini-api/terms)

Google Cloud restricts training without permission. Under Google Cloud’s online terms, flagged prompts can be retained for abuse review for up to 90 days. Before sending real documents, verify the applicable agreement and processing location, confirm exemption or an approved arrangement for abuse logging, and record the provider’s effective retention in the disclosure. Confirm caching and request/response logging are off. Keep real-document AI disabled if the approved privacy terms cannot be verified. [Google Cloud retention guidance](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention) · [Abuse monitoring](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/abuse-monitoring)

The published non-global standard rates checked November 27, 2026 are **US$0.33 per million input tokens** and **US$2.75 per million output tokens**, including reasoning. At 5,000 billable input tokens and 2,000 billable output tokens, one extraction is about **US$0.00715**. That is **US$0.72 for 100** or **US$3.58 for 500**. This estimate covers inference only. Document length and retries affect usage. PM approved a **US$5 monthly application-side inference cap**, measured before credits. Proposed volume limits are 10 attempts per workspace daily and 500 attempts across the pilot per month. Stop when any limit is reached and reconcile against provider billing. Budget alerts supplement the app cap. [Google Cloud pricing](https://cloud.google.com/model-garden/pricing) · [Cloud Billing budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets)

## Supabase production security checklist

- [ ] **Database.** Enable RLS on every application table and verify least-privilege grants and policies for all actions. Review sensitive replicated tables and publications. Leave pilot Realtime off. If added later, verify authorized Broadcast and account for the Postgres Changes delete-event limitation. Enable SSL enforcement and restrict direct database network access.
- [ ] **Organization.** Enable MFA on admin accounts and their sign-in provider, enforce organization MFA where the plan supports it, restrict admin roles, and designate a second trusted organization owner.
- [ ] **Auth.** Enable email verification, remove test phone numbers, limit OTP and email-link expiry to one hour or less, review user MFA needs, and use production SMTP from a trusted domain with link tracking disabled. Check Auth rate limits and permitted redirect URLs.
- [ ] **Threat review.** Review the threat model and OWASP Top 10, run Supabase Security Advisor, and resolve material findings. Confirm backup and recovery through the broader production checklist.

See the [setup checklist and authentication PR plan](PRIVATE_PILOT_SETUP.md) for the PM-approved architecture and activation boundaries.

1. **Managed Auth and workspace persistence (Issue #20).** Start with an authentication-only PR for Google OAuth, server sessions, and an empty protected pilot entry. Follow with workspace RLS and grants, version checks, atomic financial writes, and database recovery. Land synthetic isolation and concurrent-edit tests with persistence.
2. **Partner invitations and revocation (Issue #20).** Include owner authorization, verified-email acceptance, expiry, single use, SMTP and invite rate limits, and revocation tests with an existing session. Include task-only access tests in the Issue #4 PR if that experience enters the pilot.
3. **Private attachments and deletion (Issue #20).** Include private Storage policies, upload validation and scanning, authenticated delivery, retention disclosure, and verified deletion and file recovery. Ship with synthetic storage isolation tests.
4. **AI gateway and usage controls.** Include the separate provider enablement flag, user disclosure, approved location and retention settings, secrets, application quotas, spend cap, and manual fallback. Verify denied and over-limit requests against a stub before any paid synthetic calls.

Each PR includes its security controls, dependency and secret checks, and evidence for the relevant gate. Before Issue #5 invites go out, record the deployed version, test results, checklist evidence, recovery and deletion checks, and the PM release decision. Hold the pilot if any mandatory control lacks evidence.
