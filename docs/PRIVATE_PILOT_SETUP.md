# Private pilot setup and authentication PR plan

PM approved the security architecture and a **US$5 monthly application-side AI cap**. Resource provisioning, billing changes, and paid API activation require separate confirmation. Real-document AI starts disabled and stays disabled until the provider terms, processing location, and billing setup are verified. The steps below are for configuration after confirmation. See the [security release gates](PRIVATE_PILOT_SECURITY.md).

## 1. Supabase

1. Record the proposed staging and pilot HTTPS origins, project names, data location, plan, and administrator accounts. Use synthetic data for staging. Confirm the location, plan, and any cost with PM before creating projects.
2. Secure the organization with admin MFA, a second trusted owner, and least-privilege access. Apply the [Supabase production security checklist](https://supabase.com/docs/guides/security/production-checklist), including SSL enforcement and restrictions on direct database access.
3. In **Authentication → URL Configuration**, set the Site URL to the intended app origin and allowlist the exact app callback, such as `https://<app-origin>/auth/callback`. Keep localhost in local configuration only. Copy the provider callback URL shown in **Authentication → Sign In / Providers → Google** for step 2 below. [Supabase redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)
4. Configure Google-only sign-in for this slice and disable anonymous access and manual identity linking. Use a database allowlist of exact verified tester emails with the **Before User Created** hook. Permit approved identities to be created on first Google sign-in, and recheck the allowlist when establishing or using the pilot session so existing identities cannot bypass removal. Keep the allowlist out of the public Data API. [Supabase Auth configuration](https://supabase.com/docs/guides/auth/general-configuration) · [Before User Created hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook)
5. Configure the server with the Supabase project URL, publishable key, and canonical app origin. Store credentials in the correct environment and leave workspace tables, attachment buckets, and partner invitations for their respective PRs. When email-based flows are added, configure trusted SMTP, expiry, and rate limits before enabling them for pilot users.

## 2. Google OAuth

1. After confirmation, use the approved Google Auth Platform project. Configure **Branding**, support contact, and **Audience**. Use External if pilot users are outside the administrator’s Google Workspace organization. Use Testing during synthetic verification and add the intended tester accounts. Google’s basic identity scopes can bypass the Testing user list, so Supabase and the app enforce the actual allowlist. [Google OAuth app states](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview)
2. In **Data Access**, request only `openid`, `email`, and `profile`. In **Clients**, create a **Web application** client. Add the exact app origin as an authorized JavaScript origin and the **Supabase provider callback URL** from step 1 as the authorized redirect URI. Supabase redirects back to the separately allowlisted **app callback**. Use environment-specific clients and exact origins and redirects. [Supabase Google sign-in](https://supabase.com/docs/guides/auth/social-sign-in/auth-google)
3. Enter the client ID and secret in Supabase’s Google provider settings. Keep the secret out of frontend configuration, repository files, and diagnostics. The pilot sign-in flow uses server-side PKCE and retains only the Supabase session. Google Drive, Gmail, and offline Google access are outside the pilot.
4. After configuration, verify sign-in and sign-out with a synthetic allowed account. Verify rejection of an unlisted account and denial after removing a tester with an existing session. Confirm the consent screen shows the approved branding and scopes before pilot use.

## 3. Google Cloud AI and credits

1. Inspect the Google Developer Program benefit and the intended Cloud Billing account’s **Credits** page. Confirm which account received the **US$10 monthly credit**, its renewal and expiry, and whether the intended model’s standard input and output SKUs qualify. Google documents a monthly grant and lists eligible Vertex AI SKUs. Coverage depends on the actual billing account, eligible SKU, and available balance. The US$5 application cap applies to gross inference spend before credits. [Google Developer Program FAQ](https://developers.google.com/profile/help/benefits) · [Credit-eligible SKUs](https://cloud.google.com/skus/sku-groups/google-developer-program-premium-genai-credit)
2. Confirm the exact `gemini-3.5-flash-lite` non-global endpoint is supported and that the provider’s data processing location, agreement, and effective abuse-log retention are acceptable. Record the approved endpoint and agreement. Check whether abuse logging applies to this account and whether the required terms are available. Set real-document AI eligibility to **disabled** while any of these checks is unresolved. [Model documentation](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite) · [Retention controls](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention)
3. After explicit confirmation, create or select the dedicated AI project, link the verified billing account, and enable the Agent Platform API (`aiplatform.googleapis.com`). Use a least-privilege runtime identity with Application Default Credentials, such as an attached service account or workload federation if hosted elsewhere. Keep the OAuth client credentials separate from inference credentials. [Google Cloud authentication setup](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/start/gcp-auth)
4. Configure the pinned model and approved endpoint, disable caching and request/response logging, and leave grounding and provider-side file persistence off. Configure the monthly cap, workload limits, and kill switch in the gateway before enabling inference. Cloud billing alerts provide a separate signal. [Google Cloud retention guidance](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention) · [Cloud Billing budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets)
5. Verify the gateway offline with a stub. After paid API confirmation, make one bounded synthetic request and confirm the billed SKU, credit offset, and usage accounting in Cloud Billing after reporting catches up. Keep real documents disabled until the privacy terms, processing location, billing, and app gates are signed off. Manual quote entry stays available. Real user documents must never use the free Gemini tier.

## First bounded PR · Managed sign-in for Issue #20

**Outcome.** An approved synthetic tester can sign in with Google and reach a protected page that shows only their sign-in state. Sign-out clears the session. A removed or unlisted tester cannot use the pilot entry, even with an existing session.

1. **Authentication and sessions.** Add Google sign-in, callback, session status, and sign-out to the existing Node server. Use Supabase Auth, server-side PKCE, server-controlled verified identity checks, and a fixed same-origin post-login destination. Use `Secure`, `HttpOnly`, `SameSite=Lax` cookies for the HTTPS deployment, with bounded lifetimes, origin checks on user-initiated auth writes, and `no-store` for session responses. The browser receives sign-in state only.
2. **Tester access.** Add the minimal private tester allowlist migration and signup hook. Recheck access at application session creation and on protected requests. Deny access when the provider or allowlist cannot be verified. Keep allowlist changes operator-managed for this PR. Partner invitations and workspace roles ship later.
3. **Deployment boundary.** Add a pilot mode that fails closed without auth configuration. Serve only the sign-in flow and protected empty entry in pilot mode. Keep the current local demo available for development. The current server has local workspace and review routes, including `/api/state`, `/api/extract`, and `/api/review/*`. Exclude those routes from pilot mode until workspace authorization and the extraction gate are implemented. Do not read or migrate local workspace data from the pilot entry.
4. **Acceptance evidence.** Run offline tests with a stubbed Auth adapter for allowed and unlisted accounts, allowlist removal with an existing session, direct unauthenticated requests, expired or replayed callbacks, provider errors, tampered redirects, cookie attributes, sign-out, and denial of legacy endpoints in pilot mode. Check dependency and secret scans. Verify real Google OAuth with synthetic accounts only after setup is authorized. Follow-on PRs cover workspace persistence and RLS, partner invitations, private attachments, and AI.

### Manual staging configuration for this PR

1. After provisioning is authorized, apply `supabase/migrations/202611280001_pilot_tester_allowlist.sql` to the approved staging project. In **Authentication → Hooks**, enable **Before User Created** and select `public.pilot_before_user_created`. Complete the Google provider setup and exact redirect allowlist above. Confirm that **Allow new users to sign up** is enabled so the hook can admit an approved first-time account.
2. Add the verified email of a controlled synthetic Google account with the Supabase SQL editor. Use `insert into pilot_private.testers (email) values (lower('tester@example.test'));` with the approved address. Remove access with `delete from pilot_private.testers where email = lower('tester@example.test');`. The second command removes pilot access on the next protected request, including for an existing session.
3. Deploy only `npm run pilot` on the staging HTTPS origin. Set `VOWLY_PILOT_ORIGIN` to that origin and configure `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` from the approved project. Terminate TLS at the ingress and forward only to the pilot server on its private listener. `PORT` defaults to 3000 and `HOST` defaults to loopback. Keep query strings, request bodies, and cookies out of auth route logs. Keep this deployment on one instance. The in-memory pilot sessions last up to 30 minutes and require sign-in again after a restart. No workspace data is stored in those sessions.
4. Use two controlled synthetic Google accounts to confirm approved sign-in, rejection for an unlisted account, removal with an existing session, and sign-out. Verify legacy demo routes return 404 both signed out and signed in. Record the observed results before inviting pilot users. Local development continues to use `npm run ui` and the existing frontend dev command.

The hosted Supabase and Google checks are pending manual configuration. No live AI is needed for this PR.
